## Findings raised and corrected

These findings were sent to the implementing agents while review continued. Targeted rereading confirms the source corrections below; final focused execution evidence is recorded at the end.

1. **P1: incomplete workbook publication through classification.** `api/src/intelligence/excel/parser.js:283` classified a blank-account row as IGNORED even when it contained money, and a named row containing only a malformed monetary value as GROUP. `imports/publication.js:10` transformed/validated DETAIL rows only. Reproduce with one valid financial row plus either `['Bad account','oops']` or `[null,100]`, without a source total; the invalid row disappeared from validation and publication. Resolve classification after effective mappings using financial cell presence, then reject malformed/missing-account data. Genuine heading/blank rows should remain nonfinancial. Add workbook-level tests, including user-resolved financial columns.

2. **P1: duplicate scalar mappings silently discard money.** `api/src/intelligence/transform/normalize.js:52` overwrote each `mapped[target]`; mappings accepted two source columns targeting the same financial field. Reproduce two debit columns containing 100 and 200, both mapped to `pending_bill_debit`: publication retains 200 with no validation error. Reject ambiguous duplicate targets before publication rather than choosing the last column or assuming aggregation. Reject unsupported mapping targets and add validation regression.

3. **P1: legacy current data retains unsupported financial certification.** `api/migrations/019_intelligence_publication.sql:35` introduced `comparison_available=false`, but the original current view at line 60 returned legacy `MATCHED`/discrepancy statuses and amounts unchanged. The migration adopts legacy completed batches as current. A legacy match with no archived Tally date therefore remained counted as matched, and `sync/service.js:183` exposed `inSync=true`. Preserve historical base rows; expose unavailable comparison in current presentation when provenance cannot support a date comparison. Migration adoption coverage must include legacy matches/discrepancies.

4. **P2: exception queue stops at 500 rows.** `dashboard/service.js:listExceptions` returned a bare array under `LIMIT 500`; `ui/src/app/pages/imports/import-exceptions.ts:134` treated its length as the whole total and paginated locally. The HTTP endpoint accepted page parameters without using them. More than 500 current exceptions were silently inaccessible. Provide a counted, stable server paging contract and update the UI/tests; keep the complete bounded export independent of display paging.

5. **P2: company gap omits Tally-only balances.** `dashboard/service.js:summary` joined reconciliation through outstanding rows for `byCompany`, excluding reconciliations with null `outstanding_id`. Reproduce the existing database fixture with an unmatched Tally ledger of 7: total gap includes it, company gap omits it. Aggregate reconciliation per company independently and test agreement with the overall gap.

6. **P2: Tally-only date provenance is overwritten.** `sync/service.js:56` and `:116` selected `o.reporting_date` rather than `r.reporting_date`. Tally-only rows have no outstanding join; detail's later duplicate field overwrote the valid reconciliation date with null. Use the reconciliation reporting date for both list/detail and verify against a comparable Tally-only fixture.

7. **P2: successful ordinary retry returns a later failure.** `imports/service.js:claim` chooses the prior COMPLETED batch for an ordinary retry, but `processFile`/`startProcess` subsequently use helpers that select the latest generation. After successful generation 1 and failed reprocess generation 2, ordinary processing returns generation 2's failure instead of the selected existing success. Results/progress should honor the claimed batch. Add a retry assertion after the injected publication failure.

8. **P2: compound financial reads can mix published generations.** `dashboard/service.js:summary` performs separate pooled queries for outstanding, reconciliation and company totals. A successful publication between those statements produces one response containing different generations. Paged list/count responses have the same issue; checking export row count alone cannot detect a same-sized replacement. Wrap compound financial reads in the existing `db.readSnapshot` so one response observes one committed database snapshot.

9. **P2: nested pool acquisition prevents saturated concurrent claims.** `imports/service.js:claim` holds a transaction connection before calling `tally.snapshot`, whose `db.readSnapshot` acquires another connection. The shared pool has `max:5`. Five concurrent processing requests can occupy every client (four may wait on the same file lock), leaving the actual claimant unable to read its Tally reference until connection timeout. Reuse the pinned claim connection for a coherent reference query instead of acquiring a second pool connection. Verify at least five concurrent claims, beyond the original two-worker test.

10. **P2: shared Pager sizes disagree with validation and sync pagination.** Root found that the UI offers 250/500 rows while HTTP filters capped page size at 200 and added a failing HTTP regression before raising the cap to 500. Targeted reviewer follow-up found `sync/service.js:50` still silently capped SQL limit and offset stride at 200 while returning requested pageSize 500. With 1,000 rows the UI showed two pages of 200, leaving 600 inaccessible. Align validation, SQL limit/offset and response metadata with the same bounded page-size contract; verify the service boundary as well as mocked HTTP acceptance.
