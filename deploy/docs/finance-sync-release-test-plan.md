# Finance Sync release verification implementation plan

Approved design: a repeatable, isolated release suite covering the packaged Electron client, simulated Tally, real API/PostgreSQL, accounting results, faults and resource observations, plus a Windows/Tally acceptance checklist. No production deployment, production data or commits.

Architecture: a Windows runner creates a new local PostgreSQL cluster, runs existing regression suites and a packaged end-to-end harness, and retains timestamped reports. The harness injects synthetic configuration into the packaged desktop, serves XML over loopback HTTP, invokes the actual API, and compares published data against independently specified expectations. Manual installation and actual Tally responsiveness remain explicit release gates.

- [x] Runner: create `desktop/finance-sync/scripts/release-test.ps1` and `release-report.js`; sanitize child environments, create a fresh cluster, enforce process deadlines, always stop PostgreSQL, retain logs and aggregate pass/fail/skip evidence with release identity.
- [x] End-to-end: create `desktop/finance-sync/scripts/release-e2e.js` and supporting fixture module; verify passive startup, complete multi-company runs, day/month/full replacement and dashboard service results, failures and recovery, cancellation, serial paced requests and a configurable large synthetic export. Save timings, resource samples and per-scenario assertions to JSON.
- [x] Acceptance: document a clean Windows install, upgrade, actual Tally test company, independent totals, baseline responsiveness, cancellation and evidence collection in `deploy/docs/finance-sync-release-testing.md`.
- [x] Verification: execute the runner against the current package, inspect failures rather than relaxing assertions, review isolation/reporting, document precise results and remaining real-world gates.

Development verification on 2026-09-15 passed all 57 API tests with no database skips, 66 existing agent/desktop tests, 10 focused dashboard tests, dashboard build, packaged smoke and all 19 end-to-end scenarios with 10,000 vouchers and 20,000 balanced postings. Two added release-contract regressions also passed. Review then strengthened required-scenario validation, compared the installer's embedded ASAR/executable with the tested files, and added source/artifact stability checks. Each subsequent release run's `summary.json` is authoritative for that exact source and artifact identity; development results are not a substitute for a fresh final gate.

The harness uses local HTTPS with a temporary CA trusted only by its child processes. API test files each receive a fresh database after checking the cluster identity. Failed prefixes, duplicated/missing scenarios, skipped tests, changed source/artifacts and missing evidence cannot produce an automated pass. Installer payload verification does not perform installation or upgrading. Real Tally, Windows installation/upgrade and dashboard browser acceptance remain pending manual gates.

Local safety: database host must be loopback, database name `enterprise_dashboard_test`, role `finance_release_test`, and PostgreSQL data directory must be the newly created run directory. Simulation/API bind loopback. No private configuration files are copied into artifacts. Do not label skipped or manual tests as passed. Existing worktree changes are preserved.
